RapidTinyRec Speedrun

How fast can an LLM generative recommender decode, and is beam search even the right algorithm? Batch-1 latency on the frozen 500-user Office cohort; quality on all 4,866 Office test users.

Findings so far

  • Batch-1 cost is set by how many sequential forwards a request needs, not by beam width: one full forward on the A6000 costs 8.1 ms for 1 token and 9.8 ms for 50.
  • Certified exact decoding replaces beam search. One forward scores the prompt together with every first code; a second scores the best-bounded prefixes; an on-device test proves when the top-K is the global optimum. Checked against brute-force scoring of every item: 0 violations.
  • Office: 14.4 ms per request in one paired allocation (60× faster than HF generate, 3.9× faster than the prior BF16 stack) with top-10 proven optimal for 99.7% of users. With codebook scoring and the third code weighted 0.5 (chosen on the validation split), HR@10 rises from 0.1589 to 0.1700 (+1.11 pt, 95% CI +0.53 to +1.69) over the FP32 reference decode.
  • Industrial & Scientific: 14.0 ms vs 25.6 ms for the fully optimized full-semantics beam on the same A6000, at equal quality. No scoring rule beats MiniOneRec's own there, so the Office quality gain is dataset-specific and the rule has to be chosen on validation data.
  • Throughput: certified exact decoding serves 176 users/s on one A6000 at batch 32, vs 91 for the fully fused beam engine.
  • Why deep terms mislead: an item loses ~1.6 nats of third-code log-probability just for sharing its prefix with one sibling, and about 47% of the next-token mass leaks off the valid codebook. Beam-50 misses 14% of the exact top-10 under the training objective, yet exact search does not improve quality.
  • FP16 matches BF16's speed with about 10× better fidelity to FP32 (top-10 identical for 484 vs 374 of 500 users). Weight-only INT8/INT4 barely help at 50–200 rows per forward, and the logit lens shows SID codes are decided only in the last 6–9 of 28 layers.
  • FP8 on an L40S is slower than BF16 as implemented (15.9 vs 14.0 ms): quantizing activations at every matrix multiply costs more than the narrower weights save at 50–200 rows.

How MiniOneRec decodes, and why it was slow

MiniOneRec turns a user's history into a prompt of about 100 tokens and asks a 1.5B-parameter Qwen2 model to write the next item's semantic ID: three code tokens <a><b><c>, then a forced newline and end-of-sequence. A catalog trie allows only codes that exist (88 first codes, 2,488 two-code prefixes, 3,444 items). Beam search keeps the 50 best partial IDs at each step. An item's score is the sum of five log-probabilities, each normalized over the whole 152k-token vocabulary.

At batch size 1 every forward pass has to stream all ~3 GB of BF16 weights from GPU memory. On an RTX A6000 that alone takes about 4 ms, and a forward with 50 beam rows costs about the same as one with 1 row. Beam search makes five sequential forwards, so it is bound by how many times it re-reads the weights, not by the beam width. Hugging Face generate adds Python overhead on top and lands at 869 ms.

What changed

  • One CUDA graph per request. A hand-written Qwen2 forward and a GPU-resident constrained beam search run the whole request — prompt, three code steps, the forced suffix and the final sort — as one replay.
  • Fused forced suffix. The newline and EOS are forced, so both are scored in one two-token forward instead of two (−10 ms).
  • Trie-level prefill fusion. All 88 first codes are appended to the prompt as tree nodes (each sees the prompt and itself). One forward gives the probability of every first code and of every second code under it. This removes another sequential step and is exact.
  • Triton shared-prefix attention. One kernel per layer attends the 50 beam rows to a single copy of the prompt's keys and values plus each row's few private tokens.
  • Certified exact decoding. Every term is a log-probability, so it is ≤ 0. The score of a first-two-code prefix therefore upper-bounds the score of every item under it. After the fused forward, every item has a bound. One more forward scores the best-bounded prefixes exactly. If the K-th exact score beats every remaining bound, the returned top-K is provably the best possible under the model's own scoring rule; no beam search is needed.

What exact decoding revealed

To test what exact search changes, we computed the FP32 log-probability of every catalog item for every test user on both datasets (about 16 million items per dataset) and replayed every search and scoring choice offline. Under MiniOneRec's own score, beam-50 misses 14% of the true top-10 on Office (6% on Industrial), yet finding the true optimum does not raise HR@10. Search error is not what limits quality.

The scoring rule is what limits quality. The third code's log-probability falls by about 1.6 nats when an item shares its two-code prefix with even one sibling, and roughly half of the next-token mass leaks onto tokens that cannot be valid codes. On Office, a per-codebook softmax with the third code weighted 0.5 — chosen on the separate validation split — improves HR@10 by 1.1 points and NDCG@10 by 0.6 points. On Industrial the same tuning finds nothing better than the original rule, and dropping the forced newline/EOS terms there hurts. The rule is a real, dataset-dependent choice that should be made on validation data, and certified decoding makes any such rule exact.

Caveats

  • One model family (MiniOneRec, Qwen2-1.5B) and small catalogs; exact decoding cost grows with the number of first-level codes and with how loose the prefix bound is. The certificate tells you per request when it did not close.
  • Trie, codebook and weighted scoring change the decoding objective (a decode-time choice, like FlashRec's per-codebook softmax); full-semantics numbers are reported separately (26.1 ms in FP16, top-1 identical to FP32 for 500/500 users).
  • Industrial latencies on this page are from the A6000; an earlier Industrial run on an L40S measured 11.5 ms for certified decoding.
  • Quality is SID-level HR/NDCG; 15 catalog SIDs are shared by two items. Latency is batch 1 on one RTX A6000 with setup, compilation and graph capture excluded.
