# Full500 preparation: provenance and repeat validation

The separately frozen design covers all 500 original users in even/odd ABBA halves. Each phase has 40 graphs, 250 primary timed requests and a reverse-order untimed repeat of those same 250 users. The unchanged TF32 candidate is compared with the exact FP32 control; quality uses one primary pair per user.

`precision_full500.py` provides CPU-only scope, phase/release provenance and repeat-evidence validators. It verifies cohort content and order, phase/cache identity, expected graph/request counts, actual release digests, reverse repeat ordering, output storage separation, FP32 score sums, token/score/transition bits and ancestry. Structurally valid drift is returned with `passed=False`; untimed repeats cannot supply primary latency or inflate quality sample size.

The benchmark CLI now requires explicit `--full-cohort --full500-quality` with staged logging and exclusive scope. It records frozen full500 provenance, freezes primary timing/memory summaries, then saves each reverse-order untimed repeat before checking stability. The audit core reads those repeat files, validates frozen graph/reorder activity and includes their bit/ancestry comparisons in the stability gate. Original generation, extraction, memory and timed-loop AST boundaries remain unchanged.

The allocated-only audit entry point now binds every submitted file and executing package dependency, frozen protocol/config, real sbatch job-ID file and live Slurm allocation query before invoking the full500 audit core. OSCAR uploads its source manifest before submission, so that manifest intentionally has no job ID. The derived allocation record preserves that distinction and hashes both original files. A separate local reconciliation command compares it with the actual OSCAR submission record without running quality resampling. Missing allocation evidence fails before bootstrap; failed audit output is preserved and cannot be overwritten.

The four-phase recovery validator accepts the explicit 1,500-second generation deadline for this protocol while preserving the earlier 1,620-second default. The new full500 allocation script runs a controller with one monotonic 1,620-second deadline starting before identity checks. Generation receives at most 1,500 seconds, recovery runs in a separately bounded child, and audit receives at most 120 seconds or the remaining global time. Recovery must finish before bootstrap. Failed generation still attempts bounded recovery; failed recovery, exhausted time and late stage exits cannot authorize audit or a successful final record. Private process groups avoid nested supervisors leaving generation children outside the termination group.

Stage commands, start/exit times, recovery records, original submission-identity bytes and audit output hashes are retained. Local reconciliation checks the complete stage order and deadline as well as the OSCAR run identity, without repeating bootstrap. Nominal cleanup includes forced termination grace; it does not make a late result valid and cannot guarantee recovery after supervisor KILL or node loss. The harness/config, one-time guard and final review remain pending. CPU fixtures do not demonstrate live scheduler compatibility, GPU execution, complete ownership, dispatch or runtime budget feasibility. Submission readiness remains false.

The planning total is 1,580 seconds against a 1,620-second global work deadline, followed by nominal 180-second cleanup. This is not a bound. Ten-length TF32 setup, every-user repeats and allocated bootstrap costs remain unmeasured. Before submission, review the integrated source and deadline behavior, freeze the distinct harness/config and exclusive one-time guard, complete exact-source CI and review the budget. Full500 resampling must stay on allocated compute.

The study is exploratory and SID-level. No production loss margin is accepted, no noninferiority claim is supported, and neither this preparation nor a successful execution automatically promotes the candidate.
